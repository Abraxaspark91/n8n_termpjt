# 전사 AI 플랫폼 전환 엔터프라이즈 아키텍처(EA) 정의서
본 문서는 전사 AI 도입을 위한 클라우드·서빙 인프라·데이터베이스 플랫폼 선정 기준과 목표 아키텍처를 정의한다.
## 1. 추진 배경 및 목표
전사 각 사업부가 개별적으로 AI PoC를 진행하면서 인프라와 데이터 표준이 파편화되어 중복 투자가 발생하고 있다.
본 과제는 전사 공통 AI 플랫폼을 정의하여 서빙 인프라, 데이터 저장소, 거버넌스 체계를 표준화하는 것을 목표로 한다.
- 목표1: 신규 AI 서비스 온보딩 기간을 3개월에서 3주로 단축
- 목표2: 인프라 중복 투자 30% 절감
- 목표3: 전사 데이터 거버넌스 표준 수립
## 2. 클라우드 플랫폼 비교(AWS/Azure/GCP)
AWS는 SageMaker 및 Bedrock 생태계, Azure는 OpenAI Service 연동과 MS 오피스 생태계 통합, GCP는 Vertex AI와 BigQuery 연계가 강점이다.
비교 기준은 GPU 인스턴스 단가, 리전 가용성, 기존 SAP 연동성, 보안 인증(ISMS-P, FedRAMP) 충족 여부로 설정한다.
- AWS: p5(H100) 인스턴스 국내 리전 가용성 확인 필요
- Azure: 기존 M365/AD 연동 자산 재사용 가능
- GCP: BigQuery 기반 데이터 분석 파이프라인과의 궁합
- 3사 모두 전용회선(Direct Connect 등) 비용 별도 산정 필요
### 2.1 AI Serving 인프라: GPU 자체구축 vs 클라우드
자체 GPU 팜 구축은 3년 기준 손익분기점이 클라우드 대비 유리하나 초기 CAPEX 부담과 운영 인력 확보가 관건이다.
클라우드 서빙은 탄력적 스케일링과 최신 GPU 세대 접근성이 강점이나 장기 사용 시 단가 부담이 커진다.
- 자체구축: H100 8기 랙 기준 초기투자 약 15억원 추정
- 클라우드: 온디맨드 대비 예약 인스턴스(1~3년) 할인율 비교 필요
- 하이브리드안: 상시 트래픽은 자체구축, 피크 트래픽은 클라우드 버스팅
## 3. 데이터베이스 플랫폼 선정: SAP HANA vs Oracle
기존 ERP가 SAP ECC 기반이므로 SAP HANA로의 전환은 실시간 분석 성능과 유지보수 통합 측면에서 이점이 있다.
Oracle Exadata는 기존 DBA 인력의 운영 경험이 풍부하고 라이선스 협상력이 있다는 점에서 비교 대상이 된다.
- SAP HANA: In-memory 컬럼 스토어로 CO-PA 등 실시간 리포팅에 유리
- Oracle: 기존 백업/DR 체계 재사용 가능
- 라이선스 비용은 코어 수 기준으로 재산정 필요
### 3.1 마이그레이션 리스크 및 일정
DB 전환은 다운타임 최소화를 위해 단계적 마이그레이션(파일럿 법인 → 순차 확대) 전략을 채택한다.
데이터 정합성 검증을 위한 이중 기록(Dual-write) 기간을 최소 2주 확보한다.
- 1단계: 파일럿 법인 마이그레이션 및 검증(4주)
- 2단계: 전 법인 순차 전환(12주)
- 롤백 시나리오 및 기준 사전 정의
## 4. 목표 아키텍처(To-Be) 개요
목표 아키텍처는 서빙 레이어, 데이터 레이어, 거버넌스 레이어의 3계층으로 구성한다.
각 사업부는 공통 플랫폼 위에서 모델과 데이터 파이프라인만 온보딩하는 구조를 지향한다.
- 서빙 레이어: 컨테이너 오케스트레이션 기반 모델 서빙
- 데이터 레이어: 통합 데이터 레이크 + HANA/Oracle 연계
- 거버넌스 레이어: 모델 카탈로그, 접근제어, 감사로그
## 5. 거버넌스 및 보안 요건
전사 AI 플랫폼은 개인정보 비식별화 정책과 모델 접근권한 관리를 필수 요건으로 포함한다.
보안 감사를 위해 모든 추론 요청과 응답 로그를 90일 이상 보관한다.
- ISMS-P 인증 요건 충족
- 모델별 접근권한 RBAC 적용
- 추론 로그 90일 보관 및 이상탐지 연계
